# Производительность Пульта — 25 сентября 2026

## Текущий аудит и границы замера

Путь запроса: браузер (обычный JavaScript, без React) → локальный HTTP-сервер → очередь коротких/тяжёлых GET → PostgreSQL (`pult_ui`, максимум 3 соединения) → сохранённые снимки и агрегаты. Ozon/WB загружаются отдельным планировщиком через пулы `pult` (12) и `pult_ozon_http` (2). Открытие «Динамики бизнеса» не вызывает маркетплейсы напрямую. PostgreSQL остаётся источником истины; Redis и ClickHouse не требуются по текущим измерениям.

Снимок `GET /api/runtime-metrics` снят 25 сентября в 16:26 МСК с **ещё не обновлённого** рабочего процесса. Это накопительные средние с запуска процесса, не p95 и не замер после развёртывания. Суммарное SQL-время и ожидание пула могут превышать полное время запроса, если SQL выполнялись параллельно. Для маршрутов с 1–4 вызовами порядок ориентировочный. Поля `p50Ms/p95Ms/p99Ms` добавлены в новый код на ограниченной выборке последних 128 запросов каждого маршрута; у текущего процесса их ещё нет.

**Подтверждённое до/после в одинаковом read-only прямом вызове** `publicStores()` на рабочей БД, по 8 парных повторов: медиана **102,6 → 3,9 мс (26,5×)**, SQL **54–57 → 6**, максимум из восьми **181,9 → 6,6 мс**. Возвращаемые поля совпали; новый `snapshotRevision` добавлен отдельно для корректной инвалидации снимка. Это измерение кода, ещё не HTTP после перезапуска. Ответ `/api/stores` до изменений — около 1,8 КБ; после публикации HTTP-размер нужно измерить заново из-за нового поля.

**Повторные запросы UI:** в 21 проверенном стартовом сценарии две параллельные загрузки `/api/stores` сократились с 42 до 21 (−50%). Страница подключений ранее делала 847 `/api/data` за ~57 минут: сравнивала несопоставимые `completedAt` и `updatedAt`. Теперь при неизменных ревизиях детерминированный сценарий делает один начальный GET за это окно; при старом backend безопасный fallback — примерно один GET в 45 с. Это расчёт частоты по алгоритму и тестам, не измерение работающей версии.

**Фон:** длинный `ozon-performance` больше не удерживает в той же полосе `insights-today` и `wb-orders`. Тест удерживает первый job и доказывает запуск второго до его окончания. Реальная задержка после развёртывания ещё не измерена; следующий tick планировщика — до 30 с. Для успешного `/api/data` один повторный registry read убран: в парном прямом замере **10 → 9 SQL**; время отдельной пробы 901 → 740 мс зависит от текущей нагрузки.

**PostgreSQL:** версия 18.6, база около 14 ГБ. На снимке UI-пул был занят 3/3 и ожидали 7–10 запросов; позднее ожидание исчезло. Блокировок и deadlock не найдено. CPU ~1,2% машины, свободная RAM ~25 ГБ — ресурсов достаточно, поэтому увеличение пула не выбрано как первый шаг. У крупных таблиц `last_analyze`/`last_autoanalyze` отсутствует; `pg_stat_statements` и `track_io_timing` выключены. Точный TOP SQL по `total_exec_time`, p95 SQL-запросов и причинность 47 ГБ накопленных temp files пока получить нельзя. `EXPLAIN` без `ANALYZE` показал Bitmap Heap Scan + сортировку по `pult_live.facts`, хотя индекс порядка уже существует. Новые индексы и изменение настроек не обоснованы до обновления статистики и повторного `EXPLAIN ANALYZE`; миграций, агрегатных таблиц и внешнего кеша в этом этапе нет.

Следующий прирост вероятнее всего даст точечное ускорение `/api/data` и холодных категорий после снижения лишнего polling. Для этого нужны новый live-замер с включённым кодом, штатный `ANALYZE` в согласованное окно, затем планы фактических slow SQL. FCP/LCP/INP, 1/10/50 одновременных пользователей и HTTP p95 после изменения пока не измерены; выдавать их за достигнутые показатели нельзя.

## Проверенное в коде и оставшиеся измерения

- HTTP-метрики для **каждого недавнего запроса**: полное время, число и суммарное время SQL-запросов, ожидание пула, число и время вызовов через `fetchFn`, размер тела ответа. `GET /api/runtime-metrics` также отдаёт ограниченную историю и агрегаты по маршрутам, плюс `total/idle/inUse/waiting` каждого пула. Требуется включение нового кода в работающем процессе; до этого реальных SQL counts по основным экранам нет. В метриках нет SQL-текста, параметров, query string, cookies или содержимого ответа.
- Пулы создаются один раз при старте: runtime `max=12`, UI `max=3`, outbound `max=2`. Диагностический снимок `pg_stat_activity` показал три простаивающих сеанса `pult` и одно активное диагностическое `pult_ui`; это **не** измерение пикового ожидания. Расширять пул без статистики ожидания не стали.
- Исторические HTTP-отчёты получили отдельную очередь по одному запросу. Тест доказал, что выполняющийся отчёт не блокирует короткий GET в другой очереди. Ускорение при реальной параллельной нагрузке ещё не измерено.
- Buyer-only JS/CSS исключены из начальной страницы: минус 2 запроса и 23 865 байт без сжатия (около 6 407 байт gzip). Дублирующиеся события навигации теперь дают один `/api/stores` вместо двух. Это измерения размера и тест поведения, не замер LCP.
- Синтетический stage-тест без live-сервера: `category-sales` 251,7 → 141,4 мс (1,78×) при заданных задержках источников. Спекулятивное чтение `order-category-daily` удалено после воспроизведения гонки кеша; прежний синтетический выигрыш этого участка более не заявляется.
- Прямой read-only замер нового обработчика `/api/order-categories` на фиксированном дне: медиана 1 156,8 → 424,6 мс (2,72×). Полные ответы совпали по структуре, размеру (142 499 байт) и SHA-256. Это прямой вызов, **не** замер включённого HTTP-сервера.
- Финальная прямая read-only проба недельного источника покупателей: 10 106 → 9 096 мс (1,11×), 195 → 60 SQL-команд, 2 399 → 2 116 мс суммарного SQL-времени. Число прочитанных снимков осталось равным четырём. Повторное тёплое чтение — 4,8–4,9 мс / 3 SQL. Основные оставшиеся секунды уходят на перенос и разбор больших строк; эти результаты не заменяют HTTP-замер.
- На тех же локально прочитанных документах сборка недельной динамики категорий сравнивалась по пять раз после прогрева: медиана 1 153,5 → 851,6 мс (1,35×). Полный ответ совпал (`deepStrictEqual`, 307 170 байт и одинаковый SHA-256). Внепериодные строки исключаются после учёта новых ревизий заказа; загрузка самих документов всё ещё занимает около десяти секунд. Это замер чистой сборки, не всего HTTP-маршрута.
- Для локальных источников зафиксированы SQL counts: каталоги — 38 запросов / 131,8 мс полного чтения; insights — 95 / 119,7 мс; категории insights — 47 / 85,6 мс; WB orders — 14 / 19,5 мс; buyer snapshots за неделю — 195 / 12 398,8 мс; все товары — 38 / 644,4 мс. При повторном независимом прямом чтении тех же buyer snapshots в одном процессе: холодный вызов 10 058,1 мс / 195 SQL, сразу повторенный тёплый — 5,0 мс / 3 SQL. Это разовые прямые замеры, а не количество запросов готового экрана или гарантированная работа кеша после синхронизации. На холодном проходе суммарное SQL-время было 2 270,2 мс, поэтому перенос и разбор исходных строк в Node остаётся подтверждённым крупным вкладом.
- Инкрементальный Ozon orders уже работает для текущего дня; полная загрузка и воронка запускаются по требованию. Исправлено возобновление legacy Ozon funnel после временного сбоя: сохранённые страницы больше не запрашиваются заново. PostgreSQL funnel collector пока не имеет durable page cursor — ограничение для следующего этапа.
- `pg_stat_statements` на рабочей базе не установлен. Индексы и настройки PostgreSQL не менялись: планы и замеры конкретных slow queries до/после пока не доказали необходимость нового индекса. Redis и новые сервисы не добавлялись.

После разрешённого включения версии нужно повторить скрипт в сопоставимых условиях, снять `GET /api/runtime-metrics`, заполнить SQL count/time для главной, динамики бизнеса, категорий и покупателей, проверить свежесть и равенство финансовых ответов, затем вписать реальные значения в `После` и `×`. Время frontend rendering не подключено к конкретному HTTP-запросу: браузер собирает его отдельно, но без измерения нельзя утверждать достигнутую скорость отрисовки.
