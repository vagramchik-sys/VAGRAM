# Корпоративный спрос: аудит перед переработкой

## CURRENT STATE

- Экран `dist/buyer-order-segments-ui.js` показывает состав покупателей и короткий рейтинг товаров. Он вызывает два локальных API: `/api/buyer-order-segments` и `/api/buyer-product-segments`.
- Рабочий PostgreSQL читает сохранённые источники покупателей из `pult_live.heads` и `pult_live.facts`. Обращения к маркетплейсу при открытии страницы не требуются.
- Есть фильтры периода, площадки и магазина; отчёт отмечает неполное покрытие. SQL имеет первичные ключи фактов и индексы по магазину, домену, типу сущности, дню и порядку источника.

## PROBLEMS

- Рейтинг ограничен первыми 20 товарами; он не описывает весь ассортимент. При каждом открытии исходные документы собираются заново, поэтому большой период может быть дорогим.
- Текущий API не отдаёт раздельные агрегаты каждого SKU за текущий и предыдущий периоды, дневной ряд, категорию и показатели для B2B Score.
- Каталожные названия подбираются отдельно по магазинам. Для нового экрана нужны группировка в SQL и ограниченный объём ответа, чтобы не переносить заказы в браузер.

## AVAILABLE DATA

- В сохранённых товарных строках есть товар, заказ, площадка, магазин, время создания заказа, тип покупателя, заказанные единицы, отмены и сумма заказа, когда цена подтверждена в RUB.
- В каталоге могут быть название, артикул, категория и изображение. Наличие каждого поля нужно проверять для конкретного SKU.
- Источники сообщают полноту загрузки отдельно по магазину и схеме продаж.

## MISSING DATA

- Эти источники описывают **заказы**, не подтверждают выкуп и фактическую выручку. Для метрик выкупа потребуются статусы отгрузки/выкупа и согласование с финансовыми начислениями.
- Нет надёжного признака уникального покупателя для определения повторных покупок. В Score можно использовать только устойчивость заказов по дням, не «повторяемость клиентов».
- Для неполных дней или схем нельзя честно оценивать рост, месячный потенциал и итоговую B2B-долю. Если категория или цена товара неизвестна, сравнение с категорией и денежный потенциал недоступны.
- Для WB может отсутствовать надёжная сумма по типу покупателя. Источник должен сохранять подтверждённую сумму товарной строки в RUB, чтобы включить WB в денежную аналитику.

## IMPLEMENTATION PLAN

1. Одним набором SQL-агрегаций получить SKU и дни для выбранного и предыдущего равного периода из существующих таблиц, сохранив признаки полноты и nullable суммы.
2. На backend вычислить Score, зоны, возможности, тренды и осторожную оценку потенциала. Результат ограничить и разбить на страницы; графику отдавать только значимые точки.
3. Заменить старый экран на «Корпоративный спрос» с рабочими фильтрами, подсказками расчёта и состояниями недостаточных данных.
4. Проверить граничные формулы, API, реальные планы тяжёлых SQL при доступной базе, время открытия и соседние вкладки.

## Измерения SQL

Проверка выполнена 25.09.2026 на локальном PostgreSQL через read-only `EXPLAIN (ANALYZE, BUFFERS)` для всех магазинов. Новый API читает один агрегирующий SQL-запрос; сырые заказы в браузер не передаются. Первоначальный вариант запроса не уложился в ограничение 30 секунд даже для окна 2+2 дня. После раннего отбора дат и устранения лишнего сканирования `records`:

| Окно: текущий + предыдущий | Время SQL | Строк агрегированного ответа |
| --- | ---: | ---: |
| 2+2 дня | 0,80 с | 371 |
| 14+14 дней | 4,71 с | 579 |
| 90+90 дней | 5,30 с | 488 |

Это отдельные замеры на текущем наборе данных, а не обещание времени для любого периода и будущего объёма. Новый индекс не добавлен: после исправления выборки план и время выполнения не показали необходимости в нём. Отрисовка ограничена 200 точками на карте, таблица разбита на страницы.
