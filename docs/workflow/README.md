# Как работаем с VAGRAM

GitHub хранит общую историю исходников. Существующие приложения продолжают работать в прежних папках. Локальная копия VAGRAM содержит инструменты безопасной передачи изменений между этими папками и репозиторием.

## Для владельца

Продолжайте ставить задачи в прежних чатах. В подключенных папках сохранены инструкции для Codex: перед новой работой проверять версию из GitHub, после завершения и проверок сохранять результат. В отчете должна быть ссылка на коммит. Можно явно написать: «Сохрани готовые изменения в VAGRAM» или «Проверь обновления VAGRAM».

Это рабочий регламент для Codex, а не фоновая синхронизация каждой правки. Уже выполняющаяся задача могла загрузить инструкции раньше: она применит новые правила после их чтения или при следующем запуске. Незавершенный код не публикуется автоматически. Приложения не обновляются и не перезапускаются сами.

Для новых задач можно добавить папку локального VAGRAM как существующий проект через интерфейс Codex. Само клонирование не добавляет проект в боковую панель. Для одновременной работы используйте отдельные worktree: [официальная документация OpenAI](https://learn.chatgpt.com/docs/environments/git-worktrees).

## Команды для Codex

Команды запускаются из корня VAGRAM; Node.js 22+ и Git должны быть доступны.

```powershell
node scripts/vagram.cjs status
node scripts/vagram.cjs update marketplace-dashboard
# Теперь выполнить запрос пользователя в подключенной рабочей папке.
node scripts/vagram.cjs prepare marketplace-dashboard
```

`status` получает свежую версию GitHub и показывает локальные, входящие и конфликтующие файлы. `update` переносит только входящие изменения, сохраняя независимые локальные правки. При конфликте останавливается; до записи делает локальную резервную копию. Не вызывайте update в папке, которую в этот момент редактирует другая задача. Код сервера после обновления требует отдельного согласованного перезапуска, если это необходимо для текущей задачи.

`prepare` создает отдельную проверяемую копию на свежем `origin/main`, переносит только изменения выбранного проекта и запускает все проверки. Результат — локальный JSON для GitHub plugin; команда сама ничего не публикует. Исходные рабочие папки при подготовке не меняются. Незнакомые бинарные форматы и крупные файлы требуют отдельного рассмотрения; синхронизатор рассчитан на текстовый код и документацию.

Доступные проекты: `marketplace-dashboard`, `project-center`, `tender-dashboard`, `team-docs`, `sales-visualization`. Привязки абсолютных путей и контрольная версия находятся только в `.git/vagram/links.json`. Этот файл, payload и резервные копии не публикуются.

## Публикация через GitHub plugin

В этой установке плагин GitHub авторизован; отдельный вход Git из терминала не настроен. Не копируйте токены плагина в Git. Обычная публикация выполняется агентом следующими инструментами:

1. Прочитать JSON, путь к которому вернула команда prepare.
2. `github_create_tree`: `repository_full_name`, `base_tree_sha`, `tree_elements` из JSON.
3. `github_create_commit`: SHA нового дерева, `parent_sha = base_commit_sha`, понятное описание завершенного изменения.
4. `github_update_ref`: `branch_name = main`, SHA нового коммита, **force=false**.
5. Если ref обновлен успешно, выполнить `node scripts/vagram.cjs ack PROJECT COMMIT_SHA`.

Если шаг 4 отклонен из-за новых коммитов, повторить status/update/prepare, просмотреть и проверить объединенный результат. Не повторять ref update с force. При неопределенном результате сначала проверить фактический удаленный SHA.

`ack` сверяет опубликованный проект с подготовленным снимком и запоминает версию. Правки, появившиеся локально после prepare, сохраняются и попадут в следующую публикацию. Даже успешная публикация не является развертыванием сайта.

Тесты центра проектов в `projects/project-center/test` — адаптированные копии прежних тестов. Эта папка поддерживается в репозитории отдельно от рабочей папки приложения: при изменении поведения обновляйте соответствующие проверки там. Временные диагностические тесты из старой папки `work` не импортируются автоматически.

## Обычная работа с новой копией

Для новой разработки непосредственно в VAGRAM достаточно обычного Git/worktree без синхронизатора старых папок. Перед изменением — fetch и проверка расхождений; после — `node scripts/check.cjs`, просмотр diff, commit и публикация. При настроенном Git Credential Manager можно использовать обычный push; это отдельная авторизация пользователя.

Проверки охватывают синтаксис, типовые шаблоны секретов, тесты приложений и защиту синхронизатора от конфликтов/выхода за пределы папок. Они не заменяют проверку интерфейса или интеграций, если задача их затрагивает.

## Восстановление

Исходники доступны в истории GitHub. Локальные резервные копии перед update лежат в `.git/vagram/backups`; `before.json` содержит предыдущий текст измененных файлов, null означает, что файла раньше не было. Подготовленные worktree сохраняются в `work/candidates` до ручной уборки через Git. При аварийном завершении проверьте, что процесс из `.git/vagram/sync.lock` завершен, и только после этого удалите этот lock-файл.

Рабочие базы и секреты в GitHub не резервируются — для них нужен отдельный приватный процесс резервного копирования.
